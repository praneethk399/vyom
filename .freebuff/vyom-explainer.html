02 Alert flapping → hysteresis

The most consequential defect found live: with the fault plateau sitting exactly on a limit, noise re-armed the breach every frame. Six identical alerts fired in four seconds.

Before — instant de-escalation

Vibration hovers at the 1.2 g soft limit. Each frame below the line resets limitState to nominal; the next frame above fires a fresh warning.

After — hold-band hysteresis

De-escalation now requires the value to clear the threshold by 10 % of the soft–hard span (here 0.13 g). Escalations always fire immediately; only step-downs are delayed.

The state machine now implemented in evaluateFrame

// src/lib/thresholds.ts — the whole mechanism is these five lines
const hyst = Math.abs(rule.hardLimit - rule.softLimit) * HYSTERESIS_FRACTION;
const threshold = prev === 'critical' ? rule.hardLimit : rule.softLimit;
const cleared = rule.direction === 'above'
  ? value < threshold - hyst
  : value > threshold + hyst;
if (!cleared) continue;  // hold previous severity silently
Judgment call kept A sustained fault whose plateau genuinely oscillates ±15 K across the hard limit still re-fires roughly once a minute — that is a real re-crossing past the dead-band, which correct alarm semantics should report. Fully suppressing it would need per-parameter cooldown timers, deliberately left out of scope.

03 Replay lifecycle: three broken transitions

A dataset replay has four states — loading, playing, complete, restarted. Three of the four transitions were broken in ways a screenshot could never show; the headless lifecycle drive caught them.

04 One malformed request killed the whole API

The sharpest finding: the server died mid-verification. A POST with bare telemetry objects (missing the {ts, telemetry} wrapper) threw a TypeError that Express 4 never forwarded.

Root cause, precisely Express 4 does not forward rejected promises from async handlers, and no error middleware was mounted. Node ≥ 15 terminates on unhandled rejections. Observed live: /api/datasets answered 200, the next POST returned empty, then netstat showed nothing listening on 3001. Re-tested after the fix: malformed → 400, server alive; valid healthy window → report; faulted window → CRITICAL with “Turbine inlet over-temperature” and halved RUL.

05 Same bug class, two more hiding places

Once the picker race was fixed, re-reading the codebase for the same pattern found two more unguarded async paths — plus a millisecond collision in the alert effects.

A · Diagnostics overlap race

The 3-second tick could fire fetch N+1 while fetch N was still in flight. If N+1 (fast) resolved before N (slow), the stale report overwrote the fresh one — silently showing 6-second-old analysis as current.

// src/features/diagnostics/useDiagnostics.ts
let inFlight = false;
const tick = async () => {
  raiseDeterministicPrecursors();   // run every tick — never gated
  runOnDeviceModel();               // on-device AI is local, no race
  if (inFlight) return;            // skip this tick's fetch only
  inFlight = true;
  try { /* POST /api/diagnose */ } finally { inFlight = false; }
};

Design choice: skip rather than cancel. Skipping keeps ordering trivially correct (no newest-wins bookkeeping) and at 3 s cadence loses nothing — the skipped tick's data is fresher than the in-flight request's anyway.

B · Same-millisecond flash collision

One evaluateFrame batch can produce two criticals (TET and blade stress in the same frame). Both called flashVignette(), which used Date.now() as its React key — identical in the same millisecond → duplicate-key warning, silently dropped or doubled overlay elements. Fixed with a module-level monotonic counter:

let flashSeq = 0;  // module scope — unique across the session
flashVignette: () => set({ vignette: { id: ++flashSeq, ts: Date.now() } }),
